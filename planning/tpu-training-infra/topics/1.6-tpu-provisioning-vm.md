# 1.5 Provisioning & The TPU VM Architecture

**Topic id:** `ml-systems/tpu-provisioning-vm` · **Level:** 100 · **Difficulty:** intermediate · **Est:** ~13 min
**Status:** planned (awaiting sign-off) — closes out L100

## Scope boundary
1.5 is the **operational capstone** of L100: how you actually **provision and run on**
TPUs. It owns the GKE / Kueue / DWS-Flex provisioning path, the TPU VM lifecycle, and
the networking (MTU/firewall) a slice needs. It **builds on** 1.1 (the VM *concept*)
and 1.4 (slice shapes + the single-host / multi-host / Multislice distinction) and
puts them into practice — it does **not** re-teach them. The hands-on lab is a
**codelab** (real GKE/TPU); the in-lesson interaction is one small selector sim.

## Why / What / How
- **Why:** In 1.1 the learner understood *what* a TPU VM is. Now they must actually
  **get the hardware and run on it** — and at scale, capacity (not concepts) is the
  wall they hit. Getting provisioning + networking wrong means the job never starts.
- **What:** Provisioning Cloud TPUs operationally — the TPU VM lifecycle, single- vs
  multi-host slices, capacity modes, the GKE path (**XPK** → Kueue → DWS Flex nodes),
  storage attachment, and the host networking.
- **How:** You request a slice (e.g. `v6e-8`) via **XPK**, which drives **Kueue** to
  provision **DWS Flex-start** nodes on GKE; you get root on the host VM(s) attached
  to the chips; you **attach storage** (Hyperdisk ML / Filestore / Managed Lustre) so
  the chips aren't starved; and you configure the **DCN** networking the *hosts* need
  — **MTU 8896 + VPC firewall rules for host-to-host rendezvous**. (This is the
  VPC/DCN — **not ICI**, which is the physical chip-to-chip link and untouched by the
  VPC.) Then run.

## Learning objectives
After this topic the learner can:
- Submit a **single-host** and a **multi-host** TPU job on GKE **with XPK** (→ Kueue → GKE DWS-Flex nodes), not raw Kubernetes pods.
- Choose a **capacity mode** (on-demand · reservation · Spot · **DWS Flex-start**) for a given need.
- Configure the **DCN** networking a multi-host job needs — **MTU 8896 + VPC firewall rules for host-to-host rendezvous** — and explain why this is **DCN/VPC, not ICI** (ICI is the physical chip-to-chip link).
- Attach **high-speed storage** (Hyperdisk ML / Filestore / Managed Lustre) so the chips aren't data-starved.
- SSH into the host, run a workload, and inspect the host↔chip mapping.

## Must-learn (keep nothing else but this)
1. You never get a bare chip — you get **host VM(s)** attached to the chips and run on the host.
2. At scale, **capacity is the constraint**; **DWS Flex-start** gives ephemeral, low-cost, *queued* allocation (vs on-demand/reservation/Spot trade-offs).
3. A **multi-host** slice won't rendezvous without correct **DCN** networking — **MTU 8896 + VPC firewall rules for host-to-host** traffic. This is the VPC/DCN, **not ICI** (ICI is hardware chip-to-chip and untouched by firewalls — reinforces 1.4). Foreshadows the 2.2 rendezvous failure.
4. You submit via **XPK** (→ Kueue → GKE DWS-Flex), and you **attach storage** (Hyperdisk ML / Lustre) — a provisioned slice with no fast disk just starves.

## Key terms (glossary additions)
- `tpu vm` — *(exists)* the host VM attached to the chips.
- `dws flex-start` — Dynamic Workload Scheduler Flex-start: ephemeral, queued, low-cost capacity for bursty jobs.
- `xpk` (Accelerated Processing Kit) — Google's CLI for orchestrating TPU workloads on GKE; the real entry point (XPK → Kueue → GKE DWS-Flex nodes). No one hand-submits raw pods for multi-host slices.
- `kueue` — Kubernetes-native job queueing on GKE (quota, priority, gang-scheduling for multi-host).
- `single-host vs multi-host slice` — one host VM vs several, depending on slice size.
- `capacity mode` — on-demand · reservation · Spot · DWS Flex-start.
- `hyperdisk ml` / `managed lustre` — high-speed storage you attach so the chips aren't data-starved (the disk 2.3's data pipeline reads from).
