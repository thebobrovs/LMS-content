## Scope boundary (1.3 vs 1.1 / 1.4)
1.2 is **"the silicon": how a TPU computes a matmul.** It owns the systolic array,
bf16 precision, and arithmetic intensity. It must **not** re-teach the VM/anatomy

*names* HBM bandwidth and forward-refs MFU; depth on those is L300.

## Why / What / How
- **Why:** An engineer who doesn't grasp that a TPU accumulates on a **diagonal
  wavefront — reading each input once instead of re-fetching** — can't reason about
  memory-bound workloads, arithmetic intensity, or MFU later. This is the silicon
  foundation under every performance topic in the path.
- **What:** How a TPU multiplies matrices — the systolic array (the MXU), bf16, and
  arithmetic intensity.
- **How:** Weights sit stationary; activations stream in and are **reused** across
  cells; partial sums accumulate; the MXU is fed from HBM. High reuse → high
  arithmetic intensity → the chip stays compute-bound instead of starving.

## Learning objectives
After this topic the learner can:
- Explain **why a CPU is memory-bound** on large matmul while a systolic array is not (reuse, not a faster multiplier).
- **Trace data** through a weight-stationary array (activations stream, partial sums accumulate, the diagonal wavefront).
- Define **arithmetic intensity** and compute the **v5p ridge point (~165 FLOP/byte)**; classify a workload as compute- or memory-bound.
- Explain why **bf16** (and bigger batches) raise arithmetic intensity, and why **native FP4 (TPU 8t)** is the extreme version of that lever.
- Predict when **XLA silently zero-pads** a tensor to the MXU tile (128/256) and the memory lanes (multiples of 8 / 128) — and why that wastes compute and causes OOMs.

## Must-learn (keep nothing else but this)
1. The systolic array **reads each input from memory once and reuses it** across many MACs — that reuse, not a faster multiplier, is the TPU's throughput.
2. **Arithmetic intensity (FLOPs/byte)** decides compute- vs memory-bound; the **v5p ridge ≈ 165 FLOP/byte**. *(sets up MFU, L300)*
3. **bf16 (multiply) + fp32 (accumulate) + batching** keep the MXU fed — and **native FP4 (TPU 8t)** is the punchline: halving bytes/parameter ~doubles MXU throughput. Precision is an arithmetic-intensity lever.
4. **The Padding Trap:** dimensions that don't align to the MXU tile (128/256) or the memory lanes (multiples of 8 / 128) are **silently zero-padded** by XLA — wasting compute and on-chip memory, and a leading cause of *mysterious* OOMs on a "compute-bound" job. Align your shapes.

## Key terms (glossary)
- `systolic array`, `mxu`, `mac`, `arithmetic intensity`, `bf16`, `weight-stationary` — *(all exist in the path glossary)*.
- **`padding`** — **NEW**: XLA zero-pads tensor dims up to the MXU tile + memory lanes; misaligned shapes waste compute/memory and cause OOMs.
- **`fp4`** — **NEW**: 4-bit float, native on TPU 8t — ~2× MXU throughput by halving bytes per parameter.
