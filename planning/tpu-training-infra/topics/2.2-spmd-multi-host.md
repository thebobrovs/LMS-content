# 2.2 · SPMD across a multi-host slice

**Slug:** `ml-systems/spmd-multi-host` · **Level:** 200 · **Difficulty:** intermediate · **~14 min**
**Prerequisites:** [] · **relatedTo:** `jax-xla-stack`, `tpu-topologies`, `tpu-provisioning-vm`

## TLDR — why / what / how

**Why.** One host was easy. A multi-host slice runs the **same program on every
host** (SPMD) — and the magic is that `jax.jit` + a sharding turns that one program
into a coordinated parallel computation over ICI, with **no hand-written
communication**. When it breaks, it breaks at *rendezvous* — the DCN trap from L100
becomes a debugging story here.

**What.** The SPMD model: one binary × N hosts; `Mesh` + `PartitionSpec` +
`NamedSharding`; the partitioner (**Shardy** — JAX's only partitioner since
March 2026, successor to GSPMD) inserts the collectives; data-parallel batch
sharding as the canonical first example. `jax.distributed.initialize` and the
coordinator/rendezvous step. **Hard-knocks lab:** host 0 can't rendezvous with
host 1 — read the barrier timeout, find the DCN/firewall cause (1.8 callback).

**How.** Sim: **shard-and-collect explorer** — pick a mesh shape and a
PartitionSpec for a tensor; see which host/chip owns which shard and which
collective (all-reduce / all-gather) the partitioner inserts. Lab: codelab/notebook
(multi-host is not Colab-able; notebook simulates a mesh on CPU with
`jax.sharding` over 8 fake devices — fully runnable, per our CPU-first standard).

## Accuracy gates (verified 2026-06)

- **Shardy is THE JAX partitioner since March 2026** (migration complete; GSPMD was
  the predecessor; the temporary opt-out flag is gone). Do NOT teach GSPMD as
  current — name it as history. [openxla.org/shardy, docs.jax.dev shardy migration]
- Sharding API: `jax.sharding.Mesh` / `PartitionSpec` / `NamedSharding` — confirm
  exact current import paths at draft time.
- `jax.distributed.initialize(coordinator_address, num_processes, process_id)` —
  confirm signature; rendezvous traffic rides the **DCN** (ties to the MTU/firewall
  trap in 1.8 provisioning).
- CPU device-faking for the notebook: `XLA_FLAGS=--xla_force_host_platform_device_count=8`
  — verify it still works at draft time.

## Learning objectives

1. State the SPMD contract: identical program, per-device shards, compiler-inserted
   collectives.
2. Shard a batch across a mesh with `PartitionSpec` and predict which collective
   appears (all-reduce for gradients).
3. Explain the role of the coordinator / `jax.distributed.initialize`, and which
   network rendezvous rides (DCN, not ICI).
4. Diagnose the classic failure: one host missing at the barrier → timeout → check
   DCN reachability/firewall, not the TPU.

## Must-learn spine

- One program, N hosts: every host runs the same `main.py`; JAX glues their devices
  into one global mesh.
- Sharding is declarative: you say *how* tensors split (PartitionSpec); **Shardy**
  figures out *what communication* makes the math correct.
- Data parallelism as the canonical case: shard batch, replicate params, all-reduce
  grads over ICI rings (1.4 callback: why a long torus axis fits).
- Rendezvous: hosts find each other over the **DCN** before any ICI traffic — the
  failure mode is a *networking* bug, not a TPU bug.

## Sim spec — `spmd-shard-explorer`

A 2×4 mesh of chips (2 hosts). Pick a PartitionSpec for a [batch, features] tensor:
('data', None) / (None, 'model') / fully replicated. Canvas shows shard ownership
per chip + the collective the partitioner inserts, with bytes-on-the-wire estimate.
Checkpoint `observe-spmd` on first sharding change.

## Quiz / flashcards (≈4 each)

- SPMD in one line (same program, sharded data, inserted collectives).
- Which partitioner JAX uses today (Shardy; GSPMD = predecessor).
- Which network the rendezvous uses (DCN) vs gradients (ICI).
- What a barrier-timeout at startup usually means (a host unreachable — firewall/IP),
  and where you'd look first.
