# 1.6 · GPU or TPU? — choosing your accelerator

**Slug:** `ml-systems/gpu-or-tpu` · **Level:** 100 · **Difficulty:** beginner · **~9 min**
**Prerequisites:** [] · **relatedTo:** `why-tpus`, `tpu-cloud-architecture`
**Placement:** after Cloud TPU architecture (1.5), before Provisioning (which shifts to 1.7).

## TLDR — why / what / how

**Why.** You now know what a TPU is and how you'd consume it — but *should* you? The
real first question for any model is **GPU or TPU?**, and the answer isn't "TPU is
always better." It hinges on what your code targets, whether **XLA** can compile it,
whether you can *get* the hardware, and the workload itself.

**What.** A practical decision: the **portability ↔ peak-performance** trade-off; the
few questions that route you to GPU or TPU (code target, XLA-convertibility, resource
access, workload shape); when each genuinely wins.

**How.** A **decision-tree explorer** sim — answer a few questions, get a GPU/TPU
recommendation with the reason. Mirrors the source's number-marker decision tree.

## Accuracy gate (correct the source!)

- The source says *"TPUs are specialized for Google's TensorFlow framework."* **Wrong by
  2026.** TPUs are **XLA-based, JAX-first**, with **PyTorch-XLA** also supported;
  TensorFlow is legacy on TPU. Frame it as **XLA/JAX**, never "TPU = TensorFlow." This
  must stay consistent with 1.1 (why-tpus).
- Confirm the **portability cost**: moving a GPU/CUDA model to TPU goes through XLA and
  **usually requires some code changes** (pure CUDA kernels don't port); JAX/PyTorch-XLA
  port cleanly.

## Learning objectives

1. State the core trade-off: **hardware-specific peak performance vs portability /
   availability**.
2. Route a model to GPU or TPU using four questions: **what is the code optimized for**,
   **can XLA compile/convert it**, **can you get the resource**, **what's the workload**.
3. Say **when a TPU wins** (large-scale training, big matmuls, JAX/XLA stacks, cost per
   FLOP at scale) and **when a GPU wins** (broad framework/CUDA-kernel support, varied or
   smaller workloads, portability).
4. Know that **interoperability** (run both, switch dynamically) exists — and is an
   *advanced serving* pattern covered later (forward-ref to the L300 interop topic).

## Must-learn spine

- **The trade-off.** Optimize for one accelerator → peak performance but locked in;
  stay portable (XLA) → flexibility + availability, at some code/perf cost.
- **The decision (the tree):**
  1. **What is your code optimized for?** JAX / PyTorch-XLA → TPU-ready. CUDA / GPU
     kernels → GPU (unless convertible).
  2. **Can XLA compile/convert it?** Yes → TPU is on the table (some code changes). No
     (hand-tuned CUDA) → GPU.
  3. **Can you get the resource?** Quota, region, capacity (ties to 1.7 provisioning).
  4. **Workload shape?** Matmul-heavy large-scale training → TPU. Broad framework needs,
     custom kernels, smaller/varied → GPU.
- **When TPU wins / when GPU wins** (summary table).
- **Forward-ref:** you don't always have to choose — GKE + custom compute classes + vLLM
  can switch TPU↔GPU dynamically (L300 interop topic).
