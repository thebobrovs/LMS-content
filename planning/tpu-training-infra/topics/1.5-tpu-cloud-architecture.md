# 1.5 · Cloud TPU architecture: how you consume TPUs

**Slug:** `ml-systems/tpu-cloud-architecture` · **Level:** 100 · **Difficulty:** beginner · **~10 min**
**Prerequisites:** [] · **relatedTo:** `why-tpus`, `tpu-provisioning-vm`

## TLDR — why / what / how

**Why.** You know what a TPU *is* (the chip, the pod). But you never rent a raw chip —
TPUs are delivered as **host + chip VM units** you consume through one of a few
**paths**, and you shape jobs as **single-, multi-, or sub-host**. Without this map,
the provisioning and orchestration in the next lesson feel arbitrary. This is the
"internal architecture → cloud architecture" zoom-out.

**What.** The Cloud TPU consumption landscape: the TPU VM as the unit; the three
consumption paths and when each fits; single / multi / sub-host workload configs;
how TPUs wire into the rest of Google Cloud (storage, VPC/DCN, IAM, monitoring).

**How.** A **consumption explorer** sim — pick a *path* and a *host config*, see what
you manage vs what's managed, the control-vs-convenience trade-off, and a concrete
example. Mirrors the source's "select each marker / tab" interactions.

## Learning objectives

1. Describe the **TPU VM as the host+chip unit** you actually consume (not a bare chip).
2. Compare the **three consumption paths** — direct TPU VM, GKE, Vertex AI / Agent
   Platform — on the **control ↔ convenience** axis, and pick one for a scenario.
3. Distinguish **single-host, multi-host, and sub-host** workloads and say when each fits.
4. Situate TPUs in the **broader GCP stack** (storage, networking, IAM, orchestration)
   and explain how this topic sets up provisioning (1.6).

## Must-learn spine

- **The unit.** A TPU VM = a host VM with attached chips; you schedule *host+chip units*,
  not bare silicon (recap from 1.1, then zoom out).
- **Three consumption paths (control ↔ convenience):**
  - **Direct TPU VM** (Queued Resources / `gcloud`): full control, SSH, you manage
    everything. Research, custom stacks, fine-grained control.
  - **GKE**: containerized + orchestrated (XPK → Kueue), multi-host gang-scheduling,
    autoscaling. Production training/serving at scale. (Hands off mechanics to 1.6.)
  - **Vertex AI / Agent Platform**: fully managed — custom training jobs, tuning,
    serving/agents. Least ops, least control.
- **Host configs:**
  - **Single-host** — one TPU VM (small slices fit on one host). Simplest.
  - **Multi-host** — several TPU VMs whose chips are wired by **ICI** (one slice spans
    hosts); host processes rendezvous over **DCN**. Big models / data + model parallelism.
  - **Sub-host** — use only a *portion* of a host's chips (e.g. 1 of 4) — granular
    control + cost optimization for small jobs.
- **GCP integration:** storage (GCS, Hyperdisk ML / Filestore / Managed Lustre),
  networking (VPC / DCN), IAM, monitoring/logging.
- **Hand-off:** this is the *map*; 1.6 (provisioning) is the *mechanics* (XPK → Kueue →
  DWS, capacity modes).

## Sim spec — `tpu-consumption-explorer`

Two-axis interactive. Pick a **path** (TPU VM / GKE / Vertex) × a **host config**
(single / multi / sub). Output panel shows: the **stack** (what *you* manage vs what's
**managed**), a **control ↔ convenience** meter, the **host/chip layout** for the
config, and a one-line **example use**. Checkpoint `observe-consumption` fires on first
path switch. Optional: a Hyperstack-style architecture image (TPU VM ↔ chips ↔ pod →
the three paths).
