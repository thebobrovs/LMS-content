## TLDR — why / what / how

**Why.** M2.1 said training is a loop of gradient steps. This topic is the **infra bill** for that loop —
and it's two resources an operator owns outright: **network bandwidth** and **HBM capacity.** Each step
produces a gradient the size of the whole model that must be **synced across every device** (an
all-reduce — the dominant network cost of training), and the optimizer keeps **several copies of every
parameter** in memory (the thing that actually OOMs your chips). Get these two numbers and you can size a
cluster before you provision it.

**What.** A **gradient = a payload the size of the parameters**, summed across devices via **all-reduce**
each step (≈ 2× the payload on the wire). **Optimizer-state memory:** mixed-precision Adam holds, *per
parameter*, ~**16 bytes** — bf16 weights (2) + bf16 grads (2) + fp32 master weights (4) + Adam momentum
(4) + variance (4) — **plus activations** (batch × seq × layers, separate). So a 7B model needs ≈
**112 GB just for model+optimizer state**, before activations — which **exceeds one v5p chip's ~95 GB
HBM**, forcing sharding. *No derivatives computed anywhere.*

**How.** NEW sim **`training-memory-budget`**: stacked bars — **weights · gradients · optimizer state ·
activations** — against a per-chip **HBM** line; toggle **precision** and **sharding (N chips)** and
watch it cross from OOM to fits. Second view: reuse **`spmd-shard-explorer`** for the all-reduce *on the
wire*. Hard-Knocks: size a given model's memory; it OOMs one chip — decide what to shard to fit.

## Accuracy gates (verified; re-confirm the byte accounting at draft)

- **Gradient payload ≈ parameter count × bytes** (bf16 grads = 2 B/param). One **all-reduce** per step
  reconciles them; ring all-reduce moves ≈ **2×** the payload total. (Consistent with `spmd-multi-host`.)
- **Mixed-precision Adam ≈ 16 bytes/param** (the standard ZeRO/Megatron accounting): 2 (bf16 weight) +
  2 (bf16 grad) + 4 (fp32 master) + 4 (Adam m) + 4 (Adam v). Flag at draft that variants exist
  (12 without master copy, etc.) — present 16 as the canonical mixed-precision number with the breakdown.
- **Activations are separate** and scale with batch × sequence × layers; gradient checkpointing trades
  compute to shrink them. Keep them as their own bar, not folded into the 16 B/param.
- **Worked number:** 7B params × 16 B ≈ **112 GB** model+optimizer state > **~95 GB** v5p HBM ⇒ can't fit
  one chip ⇒ shard (data/tensor/FSDP-style). Use this as the headline operator takeaway.
- Checkpoints (the saved state) flush to **GCS over the DCN** (1.6/2.3 callback), not ICI; gradient
  all-reduce rides **ICI** in a slice. Keep the two networks straight.

## Learning objectives

1. State that a **gradient is a model-sized payload** synced by **all-reduce** every step — the network
   cost of training (bytes-on-the-wire), and which network it rides (ICI in-slice).
2. Recall the **~16 bytes/param** mixed-precision Adam footprint and *why* (weights + grads + master +
   momentum + variance), with activations counted separately.
3. **Size a model:** compute model+optimizer memory and decide whether it fits per-chip HBM.
4. When it doesn't fit, name the lever (**shard** across chips, lower precision, checkpoint activations) —
   not "buy a bigger chip."

## Must-learn spine (SRE bridge baked into each beat)

1. **A gradient is a payload, not a derivative.** Same size as the params, produced every step. *SRE
   bridge:* a fixed-size blob you must move every iteration — a recurring network transfer you budget for.
2. **All-reduce = the sync, and bytes-on-the-wire = the cost.** *SRE bridge:* a cluster-wide reduce/
   shuffle; the bottleneck is the interconnect, which is why it rides the fast ICI inside a slice.
3. **The optimizer keeps several copies of every parameter.** *SRE bridge:* per-record bookkeeping — like
   an index/replica overhead that's a multiple of the raw data; budget HBM for ~16 B/param, not 2.
4. **Capacity math decides the cluster shape.** If model+optimizer > one chip's HBM, you *must* shard.
   *SRE bridge:* classic capacity planning — the working set exceeds one node, so you partition.

## Sim spec

### NEW — `training-memory-budget` (primary view: the HBM budget)
**Concept (one):** training memory is dominated by optimizer state, and it's what OOMs the chip.
**Layout:** a **stacked bar** of per-chip memory — segments for **weights · gradients · optimizer
(m+v+master) · activations** — drawn against a horizontal **HBM capacity line** (default ~95 GB v5p,
selectable). Sliders/inputs: **parameter count** (e.g., 1B–70B), **precision** (bf16/fp8 toggles the
weight/grad bytes), **batch×seq** (activations), and **shard across N chips** (divides the per-chip
segments). A pill: **`fits`** / **`OOM by X GB`**. **The aha:** a 7B model OOMs one chip on optimizer
state alone; bump shards to 2–4 and it drops under the line. **Standard:** real `createSim`, tokens +
light/dark, reduced-motion, deterministic, one `sim.checkpoint("observe-oom")` when the learner first
drives it from OOM to fits (or vice-versa).

### 2nd view — reuse `spmd-shard-explorer`
The other half of the bill: the gradient **on the wire** (all-reduce bytes/ICI). Embed so the learner
sees both the **memory** budget and the **network** budget of the same gradient.
