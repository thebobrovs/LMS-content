## TLDR — why / what / how
**Why.** Multi-device training has a tax single-device training doesn't: **every step, every device's
gradient must be summed with every other device's** before the next step. That sync is a model-sized
transfer on the interconnect — and past some scale it, not the math, caps throughput. If an operator
can't see when training goes **communication-bound**, they'll add devices and watch utilization *fall*.
**What.** A **gradient is a payload the size of the model's parameters** (params × bytes). Reconciling it
across N devices is an **all-reduce**; ring all-reduce moves ≈ **2·(N−1)/N × payload** per device. Sync
time = **bytes ÷ interconnect bandwidth**. Compare to the step's **compute time**: if sync ≥ compute,
you're communication-bound — fixes are *a faster interconnect*, *overlapping comm with compute*, or
*bigger steps*, not more devices. (One general distinction: the **fast in-node interconnect** vs the
**slower cross-node network** — staying on the fast fabric matters; vendor-neutral.)
**How.** NEW sim **`gradient-sync-explorer`** (built, vendor-neutral): model size, # devices, interconnect
bandwidth, per-step compute, and an **overlap** toggle → payload, all-reduce bytes, sync time, a
**compute-vs-comm bar**, a **compute/communication-bound pill**, and a **speedup-vs-devices** curve that
flattens below the ideal line as comm dominates.

## Accuracy gates (verified)
- **Gradient payload = parameter count × bytes/param** (bf16 grads = 2 B/param). One **all-reduce** per
  optimizer step.
- **Ring all-reduce volume:** each device sends+receives ≈ **2·(N−1)/N × payload** (reduce-scatter +
  all-gather) → ~2× payload as N grows, roughly N-independent (ring property). Still, per-step sync time =
  payload ÷ bandwidth.
- **Sync time = bytes ÷ bandwidth.** Bandwidth is a **generic, selectable** value spanning realistic
  ranges (~50 GB/s cross-node networks up to ~900 GB/s high-end accelerator links). Headline is the
  **ratio** (sync vs compute), robust to the exact number; do NOT anchor on one vendor's figure.
- **Comm-bound condition:** sync_time ≳ compute_time ⇒ adding devices stops helping. Operator takeaway;
  quantitative-but-no-calculus (a ratio + a bar + a flattening curve).
- **Strong scaling** model: fixed global batch ⇒ per-device compute ≈ base/N shrinks while all-reduce
  stays ~flat ⇒ comm share rises with N. State this assumption.
- **Overlap** lever: frameworks overlap gradient comm with backward compute; sim's overlap toggle sets
  step = max(compute, comm) instead of compute + comm.

## Learning objectives
1. State that a **gradient is a model-sized payload all-reduced every step** — the network cost of
   distributed training — carried on the device interconnect.
2. Compute sync time as **payload ÷ bandwidth** and compare to compute → **compute-bound vs
   communication-bound.**
3. Predict what adding devices (or growing the model) does to the comm share.
4. Name the levers when comm-bound: **overlap comm/compute, a faster interconnect, bigger steps** — not
   "just add devices."

## Must-learn spine (SRE bridge per beat)
1. **A gradient is a payload, not a derivative** — same size as the params, every step. *SRE bridge:* a
   fixed-size blob you must move each iteration; a recurring, predictable network transfer.
2. **All-reduce is the sync; bytes-on-the-wire is the cost.** *SRE bridge:* a cluster-wide reduce — the
   bottleneck is the interconnect, so keep it on the fast in-node fabric, not the slow cross-node network.
3. **Sync time vs compute time decides the win.** *SRE bridge:* Amdahl/queueing — when the serial sync
   phase dominates, more workers stop helping; you've hit the communication wall.
4. **Levers are interconnect & overlap, not device count.** *SRE bridge:* you fix a network-bound system
   with faster links and pipelining, not more workers.

## Sim — NEW `gradient-sync-explorer` (built & verified, vendor-neutral)
Controls: **model size** (1B–70B), **# devices N** (2–256, ring), **interconnect bandwidth** (generic
tiers: cross-node ~50, accelerator link ~300, fast ~600, top-tier ~900 GB/s), **compute/step (1 device)**,
**overlap** toggle. Readouts: gradient payload (GB), compute/device (ms), all-reduce sync (ms), step time
(ms); a **compute|comm bar**; a **compute/communication-bound pill** + scaling-efficiency %; a
**speedup-vs-devices** log-log chart (actual vs ideal). `sim.checkpoint("observe-comm-bound")` on first
crossing. Standard: real `createSim`, tokens + light/dark, reduced-motion, deterministic. **No 2nd sim**
(the old plan's spmd-shard-explorer reuse was TPU-specific — dropped).
