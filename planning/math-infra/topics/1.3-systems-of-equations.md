> **Reframe note (why option A).** The original pitch — "this is why AI uses matrices; singular matrices
> crash ML" — is **inaccurate for this track**. Neural nets train by gradient descent and use matrices as
> *learned transformations applied by matmul* (see `what-a-neuron-learns`); they do not solve linear
> systems, invert matrices, or hit "singular matrix" crashes in normal training/inference. So this topic
> is positioned as **optional foundational literacy** — "what a matrix *is*, made concrete" — NOT as "how
> ML uses matrices." It must explicitly say so, to avoid muddying the matrix model the track built.

## TLDR — why / what / how
**Why.** A matrix like `[[1,1],[1,4]]` looks like abstract numbers. The most grounded way to *read* one:
it's a compact list of **constraints** with the variable names stripped out — exactly the capacity-vs-
budget algebra an SRE already does by hand. Get that and a matrix stops being mysterious.
**What.** Translate constraint sentences → equations → a system → a matrix. "Rack holds 40 nodes" →
`C + G = 40`; "budget $100k at $1k/CPU, $4k/GPU" → `C + 4G = 100`. The **solution** is where the
constraints agree (the intersection). The **matrix** `[[1,1],[1,4]]` is just the coefficients, stored for
a computer. **Singular** = constraints that conflict (parallel) or repeat (overlap) → no single answer.
**How.** One sim `capacity-constraint-explorer`: two constraint lines on a CPU-vs-GPU chart, a sliding
intersection (the valid config), the numpy matrix it maps to, and a "conflicting constraints" toggle that
makes the lines parallel (singular → no valid deployment).
**Honesty beat (required in the topic):** one short callout — *"ML doesn't solve systems like this; it
uses matrices as learned transformations (matmul), per [What a Neuron Learns]. This lesson is about
reading a matrix concretely; solving systems shows up in classical ML and optimization, not neural-net
training."*

## Accuracy gates (verified; re-confirm at draft)
- A linear equation in two variables is a **straight line** = all valid (C,G) combinations.
- The **solution** of a 2-equation system is the **intersection** (both constraints satisfied). For
  `[[1,1],[1,4]]·[C,G]=[40,100]` → C=20, G=20 (det = 1·4−1·1 = 3 ≠ 0).
- **Matrix translation:** the system maps exactly to coefficient matrix `[[1,1],[1,4]]` + constants `[40,100]`.
- **Singular:** parallel lines (conflict) → no solution; identical lines (redundant) → infinite solutions;
  both have determinant 0 → no unique solution. State as a property of the *constraint system*, NOT "ML crashes."
- **Do NOT claim** neural-net ML solves systems / inverts matrices / errors on singular matrices. (It
  doesn't.) Solving linear systems is a *classical-ML / optimization / numerical-LA* activity.

## Learning objectives
1. Translate an English constraint into a linear equation.
2. Read the solution of a system as the intersection of constraints.
3. Translate a system into a coefficient **matrix** (variable names stripped) + constants vector.
4. Define a **singular** system in physical terms — conflicting or redundant constraints, no unique answer
   — and know it's a property of solving systems, not of neural-net training.

## Must-learn spine (SRE bridge per beat)
1. **Equations are lazy English.** *SRE bridge:* "40 slots for CPUs and GPUs" *is* `C + G = 40` — you do
   this algebra in capacity planning already; notation just saves keystrokes.
2. **A "system" = overlapping constraints.** *SRE bridge:* you plan against rack space *and* budget; the
   solution is where both limits agree.
3. **A matrix strips the variables for the computer.** *SRE bridge:* the machine only stores the
   coefficients (multipliers); `[[1,1],[1,4]]` is just an array of multipliers — that's all a matrix is.
4. **Singular = impossible/redundant constraints.** *SRE bridge:* "max 40 nodes" AND "min 50 nodes" never
   cross — un-deployable. (Property of the constraint problem; not how training fails.)

## Sim — `capacity-constraint-explorer`
CPU-vs-GPU chart (C on x, G on y). Two lines: **rack capacity** `C + G = cap` and **budget**
`C + 4G = budget` (CPU $1k, GPU $4k). Sliders move `cap` and `budget`; the **intersection dot** slides to
the valid config (live "20 CPUs, 20 GPUs" readout, only when both ≥ 0). A panel shows the **numpy matrix**
`[[1,1],[1,4]]` + constants. A **"conflicting constraints (singular)"** toggle swaps the budget line for a
second `C + G = …` line → parallel → red "Impossible deployment — singular: no unique solution," and the
matrix flips to `[[1,1],[1,1]]` (det 0). Standard: real `createSim`, tokens + light/dark, reduced-motion,
deterministic, `sim.checkpoint("observe-singular")` when the learner first triggers the singular case.
