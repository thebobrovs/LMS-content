## TLDR — why / what / how

**Why.** An operator's most baffling failure is the **mysterious OOM**: a job that "should fit" by
back-of-envelope math dies anyway. The cause is almost always **shape**, not size. Accelerators are
*rigid*: the matrix unit works in fixed **128×128 tiles**, and the compiler **silently zero-pads** any
dimension that isn't a multiple of the tile. A 129-wide matrix becomes 256-wide — you pay compute and
memory for a wall of zeros. Knowing this turns "why did it OOM?" into a 10-second diagnosis.

**What.** A **tensor** is just a shaped N-D array; its **shape** sets its memory footprint and how it
maps onto the MXU. **Padding math:** dimensions round up to the next multiple of **128** (256 on
v6e/v7), and vector lanes to multiples of **8**; the wasted area is `(padded/real)² − 1` for a square
tile. Why static shapes at all: the chip needs **pre-allocated, fixed layouts** before it runs (the
trace/compile story from the TPU path) — so a changed shape forces a recompile, too.

**How.** NEW sim **`matmul-tiler`**: drag the M/K/N dimensions of a matmul, watch the 128×128 tiling
grid, the **padded zeros light up**, and a live **wasted FLOP / wasted memory %** readout. Hard-Knocks:
a job OOMs on a slice it should fit — spot the `128k+1` dimension, round it to a multiple of 128, and
watch the footprint drop.

## Accuracy gates (verified; re-confirm at draft)

- **MXU tile = 128×128** (v5p and most gens); **256×256** on v6e/v7. XLA zero-pads matmul dimensions up
  to the tile, and memory lanes up to multiples of **8**. (Same `padding` fact as the TPU path glossary.)
- A dimension rounds up to the **next multiple of 128** (or 256). Example: **129 → 256** → for a square
  matrix `(256/129)² − 1 ≈ 2.9` ⇒ **~290% wasted** compute/memory on padding alone. Use a cleaner
  worked example at draft (e.g., 130 → 256, or 1,025 → 1,152).
- Padding burns **both** compute (FLOPs on zeros) **and** HBM/VMEM (storing zeros) — the latter is the
  surprise-OOM mechanism.
- **Static shapes:** shapes freeze at trace/compile time; change a shape and it re-traces/recompiles —
  tie back to `math-infra` siblings and `jax-xla-stack`. (Why dynamic Python can't run directly: the
  device needs fixed pre-allocated layouts.)
- Pick dims that are **multiples of 128** (and 8 for vector dims); the practical operator rule.

## Learning objectives

1. Define a **tensor** and its **shape**, and say why shape (not just element count) sets the footprint.
2. Explain the **128 tile** and that misaligned dims are **zero-padded** to the next multiple.
3. Compute, roughly, the **wasted compute/memory** for a misaligned dimension.
4. Diagnose a **surprise OOM**: first question = "are the batch/feature dims multiples of 128?"

## Must-learn spine (SRE bridge baked into each beat)

1. **A tensor is a shaped buffer; the shape is the memory contract.** *SRE bridge:* like a struct's
   field sizes or a packet's fixed layout — the dimensions, not a vague "size," decide what's allocated.
2. **The chip thinks in 128 tiles.** Anything off-grid gets rounded up with zeros. *SRE bridge:*
   **block/page alignment** — a 4 KB page holds a 1-byte file; a 129-wide matrix takes a 256-wide tile.
   Same rounding tax, bigger blocks.
3. **Padding costs compute AND memory — and the memory cost is the OOM.** *SRE bridge:* internal
   fragmentation — you provisioned for the data, but you're paying for the slack to the next boundary.
4. **Rigid shapes are why it's fast (and why it recompiles).** *SRE bridge:* pre-allocated fixed buffers
   beat malloc-on-the-fly; the price is that changing the shape invalidates the plan (a recompile).

## Sim spec

### NEW — `matmul-tiler` (primary view: the tiling geometry)
**Concept (one):** a matmul's dimensions snap to 128 tiles, and the off-grid remainder is wasted zeros.
**Layout:** sliders for **M, K, N** (the `[M,K]·[K,N]` matmul); a grid showing the real matrix vs the
**padded-up-to-128** extent with the **padded cells shaded** as zeros; readouts: real vs padded element
counts, **wasted memory %**, **wasted FLOP %**, and the padded shape (e.g., `129 → 256`). Preset chips:
"v5p (128)" vs "v6e/v7 (256)" to show the bigger tile rounds harder. **The aha:** nudge a dim from 128
to 129 and watch waste jump from 0% to ~75–290%. **Standard:** real `createSim`, tokens + light/dark,
reduced-motion, deterministic, one `sim.checkpoint("observe-padding")` when waste first exceeds ~0.

### 2nd view — reuse `arithmetic-intensity-calculator`
It already carries the padding trap alongside intensity; embed it so the learner connects shape →
padding → the same roofline lever from M1.1.
