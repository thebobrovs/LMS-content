## TLDR — why / what / how

**Why.** This is the one math topic the audience already half-knows — they're network engineers. A
supercomputer's interconnect is just a **graph**, and the questions that decide performance (how far is
the farthest hop? where's the bandwidth bottleneck if I cut the cluster in half?) are **graph metrics**
they use every day under different names. Give them the vocabulary map — torus ↔ graph, twist ↔ diameter
optimization — and "why this slice shape is faster" becomes obvious instead of magical. No proofs.

**What.** The torus as a **graph**: nodes (chips) + edges (links), **3-D coordinates**, and **modulo
arithmetic** for the wrap-around edges that close the ring. Three metrics that decide collective
performance: **hop count / network diameter** (worst-case shortest path = worst-case latency),
**bisection bandwidth** (min links cut to split the network in half = the cross-section throughput), and
how **"twisting" a torus** is a graph trick that **shrinks diameter and raises bisection** for the same
chips. Tie to M2.2: the all-reduce you just budgeted *rides this graph*, so the graph's metrics are its
speed limit.

**How.** NEW sim **`network-graph-explorer`**: an abstract **node/edge graph** (not the 3-D hardware
view) with live **diameter / bisection / hop-count** readouts; reshape the grid, toggle **wrap-around**
and **twist**, and watch the metrics move. Second view: reuse **`torus-3d`** for the physical wiring the
graph abstracts. Hard-Knocks: two slice shapes with the *same chip count* — pick the one with **lower
diameter / higher bisection** and justify it in graph terms.

## Accuracy gates (verified; re-confirm at draft)

- A TPU slice/pod is a **k-ary n-cube (torus)**: chips at integer 3-D coordinates, each linked to
  neighbors; **wrap-around edges** (coordinate arithmetic **mod** the axis length) close each ring into a
  torus. (Consistent with `tpu-topologies`: 6 ICI links/chip on v5p, 3-D torus; 4×4×4 = 64-chip cube.)
- **Network diameter** = the longest shortest-path (max hops between any two nodes) → worst-case latency.
  A ring of n has diameter ⌊n/2⌋; the wrap-around halves it vs a line.
- **Bisection bandwidth** = the minimum number of links you must cut to split the network into two equal
  halves × per-link bandwidth → the throughput bottleneck for all-to-all / large all-reduce traffic.
- **Twisting** a torus (skewing the wrap-around connections) **reduces diameter** and **raises bisection**
  for the same node count — a real lever the topology lesson cites. State the *effect*, not a proof.
- Map names explicitly: hop count ≈ latency in hops; diameter ≈ worst-case path; bisection ≈ the
  cross-section bottleneck an SRE already reasons about for spine/aggregation layers.
- Keep graph theory at **intuition level** — no formal definitions/derivations (that's L300+).

## Learning objectives

1. See the torus as a **graph**: nodes, edges, 3-D coordinates, and **modulo wrap-around**.
2. Define **diameter** (worst-case hops → latency) and **bisection bandwidth** (cut-in-half throughput) in
   the network-engineering terms the learner already owns.
3. Explain why **twisting** the torus helps — lower diameter, higher bisection, same chips.
4. Connect to M2.2: the **all-reduce rides this graph**, so the graph's metrics cap its speed; slice
   *shape* is therefore a performance lever.

## Must-learn spine (SRE bridge baked into each beat)

1. **The interconnect is a graph.** Nodes + edges; coordinates address them. *SRE bridge:* it's a network
   fabric like any you've drawn — Clos/spine-leaf is a graph too; the torus is just a different shape.
2. **Wrap-around = modulo, and it halves the diameter.** *SRE bridge:* closing a line into a ring (mod the
   length) gives a second path around — like a redundant ring link that cuts worst-case hops in half.
3. **Diameter = worst-case latency; bisection = the cross-section bottleneck.** *SRE bridge:* exactly the
   two questions you ask of any fabric — farthest hop (tail latency) and the throughput if traffic
   crosses the middle (oversubscription at the spine).
4. **Twisting is a topology optimization.** Same hardware, better metrics. *SRE bridge:* re-cabling the
   fabric for a lower diameter / fatter bisection — a layout choice, not more gear.
5. **The collective's speed is the graph's speed.** *SRE bridge:* your all-reduce is the workload; the
   graph is the network SLO it runs against — shape the slice to fit the traffic.

## Sim spec

### NEW — `network-graph-explorer` (primary view: the graph abstraction)
**Concept (one):** topology choices are graph-metric choices — diameter and bisection move with shape.
**Layout:** an abstract **node/edge graph** (start 2-D for clarity, e.g., an n×n mesh) with toggles:
**wrap-around** (line→ring→torus), **twist**, and grid **shape** (e.g., 4×16 vs 8×8 vs 16×4, same 64
nodes). Live readouts: **diameter (max hops)**, **bisection (links cut)**, **avg hop count**; highlight
the **diameter path** and the **bisection cut** on the graph. **The aha:** flip wrap-around on and watch
diameter halve; pick a squarer shape and watch bisection rise — same node count, better network.
**Standard:** real `createSim`, tokens + light/dark, `prefers-reduced-motion`, deterministic (computed
metrics, no `Math.random`), one `sim.checkpoint("observe-diameter")` when the learner first improves a
metric (twist on, or reshape).

### 2nd view — reuse `torus-3d`
The physical 3-D wiring the graph abstracts — so the learner connects "abstract graph metric" to "the
actual cube of chips" from the TPU path.
