# M2.3 · Topology graphs — build blueprint (vendor-neutral)

**Slug:** `math-infra/topology-graphs` · **Level:** 200 · **Difficulty:** intermediate · **~12 min**
**Prerequisites:** `math-infra/gradients-and-bandwidth` · **relatedTo:** `math-infra/what-is-a-tensor`
**Path:** `math-infra` (L200) · **Audience:** infra/SRE ("Sam") — strong network background. **Vendor-neutral.**

> **Vendor-neutral note.** A cluster interconnect is a **graph** regardless of vendor — GPU clusters use
> NVLink/NVSwitch inside a node and an InfiniBand **fat-tree (Clos)** across nodes; some accelerators wire
> a **torus**; all of it is nodes + links. Teach the universal graph metrics (**diameter**, **bisection
> bandwidth**, **hop count**) and how **topology shape** moves them. Name torus/fat-tree only as *examples*
> of shapes, never as the framing. No TPU-specific terms (ICI, OCS, slice, twist).

## TLDR — why / what / how
**Why.** This is the one math topic the audience already half-knows — they're network engineers. The
interconnect that the M2.2 all-reduce rides is just a **graph**, and the two questions that decide
collective performance — *how far is the farthest hop?* and *what's the throughput if traffic crosses the
middle?* — are graph metrics they use daily under other names (tail-latency hops, spine oversubscription).
Give them the vocabulary map and "why this cluster shape is faster" stops being magic.
**What.** The interconnect as a **graph**: nodes (devices) + edges (links). Two metrics that cap
collectives: **network diameter** (worst-case shortest path = worst-case latency in hops) and **bisection
bandwidth** (links you must cut to split the network in half × per-link BW = the cross-section throughput
limit for all-reduce / all-to-all). How **shape** moves them: **wrap-around** (line→ring, mesh→torus)
halves diameter; a **squarer** grid raises bisection — same node count, better network. Tie to M2.2: the
all-reduce *rides this graph*, so the graph's metrics are its speed limit, which is why job placement and
cluster shape are performance levers.
**How.** NEW sim **`network-graph-explorer`**: an abstract node/edge graph — pick **rows × cols**, toggle
**wrap-around** (mesh↔torus) and **1-D mode** (line↔ring) — with live **diameter / avg hops / bisection**
readouts, the **diameter path** and the **bisection cut** highlighted. Aha: flip wrap-around and watch
diameter halve; square up the grid and watch bisection rise.

## Accuracy gates (verified; re-confirm at draft)
- **Graph model:** nodes = devices, edges = links. A 2-D grid (mesh); add wrap-around edges on each axis
  → torus. 1-D: line; close it → ring.
- **Diameter** = the longest shortest-path (max hops between any two nodes) → worst-case latency. Compute
  via BFS from every node (graphs are small, ≤ ~100 nodes — exact, deterministic). Ring of n: ⌊n/2⌋ vs
  line's n−1 (wrap-around roughly halves it).
- **Bisection** (structured graphs, computed analytically, not min-cut): line = 1, ring = 2; R×C mesh =
  min(R,C) (cut perpendicular to the longer axis); R×C torus = 2·min(R,C) (wrap-around adds a second cut).
  Bisection × per-link bandwidth = cross-section throughput. **Squarer grid ⇒ larger min(R,C) ⇒ higher
  bisection** for the same node count (8×8 mesh = 8 vs 4×16 mesh = 4).
- **Fat-tree / Clos (spine-leaf):** the topology GPU/datacenter networks use most; it's a *tree* graph
  engineered for **full bisection** (non-blocking) at the cost of more switches/links. Mention as the
  SRE-native example; don't need to draw it in the sim.
- Keep graph theory at **intuition level** — no formal proofs (that's L300+).

## Learning objectives
1. See a cluster interconnect as a **graph** (nodes + links) and name common shapes (ring, mesh, torus,
   fat-tree/Clos) as graphs.
2. Define **diameter** (worst-case hops → latency) and **bisection bandwidth** (cut-in-half throughput) in
   the network terms the learner already owns.
3. Predict how **shape** changes the metrics — wrap-around halves diameter; squarer raises bisection.
4. Connect to M2.2: the **all-reduce rides this graph**, so its metrics cap collective speed; cluster
   shape and job placement are therefore performance levers.

## Must-learn spine (SRE bridge per beat)
1. **The interconnect is a graph.** *SRE bridge:* it's a fabric like any you've drawn — spine-leaf/Clos is
   a graph too; ring/mesh/torus are just other shapes.
2. **Wrap-around halves the diameter.** *SRE bridge:* closing a line into a ring gives a second path
   around — like a redundant ring link that cuts worst-case hops.
3. **Diameter = worst-case latency; bisection = the cross-section bottleneck.** *SRE bridge:* exactly the
   two questions you ask of any fabric — farthest hop (tail latency) and throughput across the middle
   (spine oversubscription).
4. **Shape is a lever; full-bisection fabrics cost more gear.** *SRE bridge:* a fat-tree buys non-blocking
   bisection by adding switches; a torus is cheaper but blocking — the classic cost-vs-throughput call.
5. **The collective's speed is the graph's speed.** *SRE bridge:* your all-reduce is the workload; the
   graph is the SLO it runs against — shape/place the job to fit the traffic.

## Sim — NEW `network-graph-explorer`
Abstract node/edge graph. Controls: **rows** and **cols** sliders (e.g., 2–10 each), **wrap-around**
toggle (mesh↔torus), **1-D mode** toggle (collapse to a single line/ring). Readouts: **nodes**,
**diameter** (max hops), **avg hops**, **bisection** (links cut). Highlight a **diameter path** (a
worst-case shortest path) and the **bisection cut** (the mid-line and the edges it severs). Aha sequence:
start 4×16 mesh (low bisection, big diameter) → square to 8×8 (bisection up) → wrap-around on (diameter
down, bisection doubles). Standard: real `createSim`, tokens + light/dark, reduced-motion, deterministic
(BFS metrics + analytic bisection, no Math.random), `sim.checkpoint("observe-topology")` when the learner
first improves a metric.

## Dedup
- `gradients-and-bandwidth` (M2.2) owns the *all-reduce cost* (bytes ÷ bandwidth). This topic owns the

- Hardware-specific topologies (a vendor's torus/OCS, ICI link counts) live in the separate TPU path, not
  here. This topic stays at the graph-abstraction level. No shared TPU sims.
