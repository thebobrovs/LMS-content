## TLDR — why / what / how

**Why.** Every infra engineer meets `bf16`, `fp16`, `fp4` and wonders "why not just use normal
floats?" The answer is pure systems: **a number's byte width is a throughput lever.** Halving the
bytes a value occupies halves the traffic on the memory bus, which **doubles arithmetic intensity**
and keeps the expensive matrix unit fed instead of starved. The cost is range/precision — and getting
that trade wrong makes training silently diverge (overflow/underflow). This is the first number an
operator reasons about when sizing memory and picking a config.

**What.** What a float actually is (sign · **exponent = range** · **mantissa = precision**); why
**bf16** keeps fp32's 8-bit exponent (same dynamic range) but drops mantissa bits, while **fp16**
spends bits on precision and **overflows past ~65,504**; **fp4** as the extreme (native on TPU 8t);
and the bridge to performance: **arithmetic intensity = FLOPs ÷ bytes moved**, and the roofline
**ridge** that separates memory-bound (starved) from compute-bound (saturated).

**How.** Two views. NEW sim **`number-format-explorer`**: drag a value, watch the sign/exponent/mantissa
bits and where it *rounds* or *overflows* across fp32/bf16/fp16/fp4 — the format itself. Second view:
reuse **`arithmetic-intensity-calculator`** to connect bytes → intensity → the roofline ridge. Plus a
Hard-Knocks: find the magnitude where fp16 → `inf` but bf16 holds, and say why from the exponent bits.

## Accuracy gates (verified facts; re-confirm at draft)

- **bf16** = 1 sign + **8 exponent** + 7 mantissa bits. Same exponent (dynamic range) as fp32; fewer
  mantissa bits (coarser precision). 2 bytes. The default matmul input type on TPUs.
- **fp16** = 1 + **5 exponent** + 10 mantissa. More precision than bf16, but the 5-bit exponent
  **overflows to inf above ~65,504** — the classic "why training blew up in fp16."
- **fp32** = 1 + 8 exponent + 23 mantissa, 4 bytes — the baseline.
- **fp4** = 4-bit float, native on **TPU 8t**; ~¼ the bytes of bf16 → roughly doubles MXU throughput
  by cutting memory traffic per FLOP. (Used for inference + increasingly parts of training.)
- The MXU multiplies in bf16 but **accumulates partial sums in fp32** (range matters for the running
  sum) — the reason the systolic-array lesson gives for fp32 accumulation. Keep consistent with 1.3.
- **Arithmetic intensity = FLOPs / bytes moved.** v5p **ridge ≈ 165 FLOP/byte** (459 TFLOP/s ÷ 2.8
  TB/s). Below it = memory-bound; above = compute-bound. (Same figure used across the TPU path.)
- Lower precision **raises** arithmetic intensity (fewer bytes for the same FLOPs) — that's *why* it
  helps, not just "smaller is cheaper."

## Learning objectives

1. Explain a float as **range (exponent) vs precision (mantissa)** without any math — and why bf16
   trades precision for range while fp16 does the opposite.
2. State the systems reason for low precision: **fewer bytes → higher arithmetic intensity → MXU stays
   fed** (not just "uses less memory").
3. Predict the failure: a value past fp16's range **overflows to inf**; bf16 survives because it kept
   fp32's exponent.
4. Place a workload on the **roofline**: given FLOPs and bytes, say memory-bound vs compute-bound and
   which lever (precision, batch) moves it.

## Must-learn spine (SRE bridge baked into each beat)

1. **A number has a byte cost, and that cost is a bus-traffic lever.** *SRE bridge:* it's a wire-format
   / compression choice — like int32 vs int64, or a compact serialization. Halve the bytes, halve the
   bandwidth you spend moving it.
2. **Exponent = range, mantissa = precision.** bf16 keeps fp32's reach but takes coarser steps; fp16
   takes fine steps but can't reach far → it overflows. *SRE bridge:* range = the magnitude window;
   blow past it and you get `inf`/`NaN` — the numeric equivalent of an integer overflow wrapping.
3. **Why this keeps the chip busy: arithmetic intensity.** FLOPs per byte. Lower precision = fewer
   bytes for the same math = higher intensity = the matrix unit isn't waiting on memory. *SRE bridge:*
   compute-bound = CPU pegged (good, you're using what you paid for); memory-bound = waiting on the bus
   (bad, expensive silicon idling).
4. **The roofline ridge is the line you're trying to cross.** *SRE bridge:* a saturation threshold —
   below it your bottleneck is bandwidth, above it your bottleneck is the compute units; you tune to
   get above it.

## Sim spec

### NEW — `number-format-explorer` (primary view: the format itself)
**Concept (one):** the same real number is stored differently — and lossily — by each float format.
**Layout:** a number input/slider; four rows (fp32 / bf16 / fp16 / fp4) each showing the **bit layout**
(sign · exponent · mantissa, color-coded), the **stored value** (with rounding error), and a state pill
(`exact` / `rounded` / **`overflow → inf`** / `underflow → 0`). A small "range bar" per format marks
where the chosen value sits relative to that format's max. **The aha:** push the value up past ~65,504
and fp16 flips to `overflow → inf` while bf16 still shows a (rounded) number — range vs precision, seen.
**Standard:** real `createSim`, Hyperstack tokens + light/dark, `prefers-reduced-motion`, deterministic
(no Math.random), one `sim.checkpoint("observe-overflow")` on the first time a format overflows.

### 2nd view — reuse `arithmetic-intensity-calculator`
Connects the format choice to performance: fewer bytes → higher FLOP/byte → crossing the v5p ridge.
Embedded after the format sim so the learner sees *both* "what the bits do" and "why it matters."
