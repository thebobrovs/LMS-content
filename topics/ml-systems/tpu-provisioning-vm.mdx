## The one-line summary

Knowing *what* a TPU is (topic 1.1) isn't the same as *getting one and running on
it*. In practice you submit a job with **<Term id="xpk">XPK</Term>**, which queues
through **<Term id="kueue">Kueue</Term>** and provisions GKE nodes; you land on a
host VM attached to the chips; you attach storage; and — the part people get wrong —
you configure the **DCN** networking the hosts need. At scale, *capacity*, not
concepts, is the wall you hit.

## How you actually run a job

You rarely hand-write Kubernetes for a multi-host slice. The real path is:

> **XPK → Kueue → GKE provisions DWS Flex-start nodes → host VM(s) ↔ chips.**

You request a slice (say `v6e-256`); <Term id="xpk">XPK</Term> drives
<Term id="kueue">Kueue</Term> (quota, priority, gang-scheduling) which provisions the
nodes; you get **root on the host VM(s)** physically attached to the chips, install
JAX or PyTorch-XLA, and run.

## The capacity wall

At scale you can't always *get* the chips — so you choose a **capacity mode**:

- **On-demand** — available now, full price.
- **Reservation** — committed, guaranteed, never preempted (for long runs).
- **Spot** — cheapest, but preemptible any time.
- **<Term id="dws flex-start">DWS Flex-start</Term>** — ephemeral, **queued**, low
  cost; not preempted once it starts (great for bursty experiments).

## The networking trap (DCN, not ICI)

A **multi-host** slice is several host VMs whose chips are wired by
<Term id="ici">ICI</Term>. But the *host processes* must rendezvous — and that
traffic rides the **<Term id="dcn">DCN</Term> (the VPC)**, not ICI.

<Callout type="warning">
**MTU 8896 and VPC firewall rules are DCN/host-to-host configuration — not ICI.**
ICI is a physical chip-to-chip link and never touches the VPC. Get this wrong and
your hosts can't rendezvous (the failure you'll debug in L200). Checkpointing to GCS
and Multislice traffic also ride the DCN.
</Callout>

## Don't forget the disks

A slice with no fast storage just starves. Attach high-throughput storage —
**Hyperdisk ML**, Filestore, or Managed Lustre — so the chips stay fed. That disk is
exactly what your input pipeline (L200) will read from.
